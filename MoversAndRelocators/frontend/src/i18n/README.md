# Translations (English, Arabic, Turkish, Spanish, French, Portuguese)

## How it works
- `src/i18n/index.tsx` — `useT()` (components), `t()` (plain modules), `serverMessage()` (API errors), `formatNumber/formatDate/formatDateTime`.
- Texts: `src/i18n/locales/<language>/<namespace>.json`, looked up as `t('<namespace>.<key>')`. Nested objects are allowed: `{"inventory": {"title": "…"}}` → `t('sales.inventory.title')`.
- English (`en`) is the source and fallback. Every key must exist in all six folders: `en ar tr es fr pt`.
- Placeholders: `{name}` filled from params — `t('sales.itemsLoaded', { count: 3, lead: 'L-12' })`. Numbers are formatted for the language.
- Plurals: add `_one` / `_other` (and for Arabic also `_zero`, `_two`, `_few`, `_many`) and pass `count`:
  `"itemsLoaded_one": "{count} item loaded"`, `"itemsLoaded_other": "{count} items loaded"`.
  Arabic: `_zero`, `_one`, `_two`, `_few` (3–10), `_many` (11–99), `_other`. Only languages that need a form must have it; `_other` is always required.
- `common.json` (shared words: save, cancel, delete, status, errors…) is owned centrally — reuse its keys, do not edit it.
- `server.json` is the catalog of messages the API sends as codes; `en/server.json` is generated by `node tools/i18n/extract-server-messages.mjs` (never edit by hand). The other languages translate it key by key.

## Server messages
The API sends errors as `{ code, params, message }`. `request()` in `api.ts` turns them into `t('server.<code>', params)`
(falling back to the English `message`), so `catch (e) { message.error(e.message) }` already shows the user's language.
After adding or changing a server message, run the extractor and translate the new keys in `locales/*/server.json`.

## Converting a component
```tsx
import { useT } from '../i18n'
export function Thing() {
  const { t } = useT()
  …
  <Button>{t('common.save')}</Button>
  message.success(t('sales.inventorySaved'))
  <Form.Item label={t('sales.customerName')} rules={[{ required: true, message: t('common.required') }]}>
```
- Call `useT()` inside the component (so it re-renders when the language changes). Constants defined outside a component
  (option lists, column titles, step names) must be built inside the component or hold keys translated at render.
- Translate every user-visible string: labels, placeholders, titles, buttons, tooltips, table column titles, empty
  states, alerts, confirm texts, `message.*`/`notification.*` calls, `aria-label`, `title=` attributes, Modal titles.
- Do not translate: data values (names, numbers, codes), CSS classes, API URLs/fields, enum values sent to the server
  (e.g. `'ITEM'`, `'NOT_NEEDED'` — translate only their displayed labels), console logs, product name "Crateway", model ids.
- Sentences with values: one key with placeholders, never string concatenation (word order differs by language).
- Keys: camelCase, grouped by screen/feature, meaningful (`pickups.collection.approveTitle`, not `pickups.text12`).
- Arabic is right-to-left: avoid `marginLeft`/`left` in inline styles — use `marginInlineStart`/`insetInlineStart`.
- Dates/numbers: prefer `formatDate`/`formatDateTime`/`formatNumber` from `i18n` over `toLocaleString()` with no locale.

## Checks
- Type-check: `npx tsc -p tsconfig.app.json` (from `frontend/`). `tsc --noEmit` alone checks nothing here.
- `node tools/i18n/check-locales.mjs` (from the repo root) lists keys missing in any language, placeholder mismatches, and keys used in code but missing from `en`.
